# Feedback and Enforcement

## Purpose

This area defines RoadAhead's stable product boundary for **feedback severity and enforcement-profile semantics** in POC V1.

Feedback and enforcement is the **advisory severity layer** RoadAhead uses to characterize how a driver approached and passed an applicable speed-relevant event. It exists so that the driver-facing surface can answer a single, deliberately narrow question — *how does the way the driver is approaching, or has passed, the current event compare to the event's target plus a configurable severity buffer?* — without that question being entangled with legal enforcement, jurisdictional law, camera capture certainty, target-speed redefinition, or UI smoothing.

Feedback and enforcement is **not legal enforcement truth**: it does not assert that any approach speed or pass speed constitutes a violation, a fine, a confirmed camera capture, or a guaranteed enforcement outcome ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truths 3, 4, 5). It is **not a speed-reference**: the `target_speed_kmh` exposed by an `approach_target` speed reference ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 4, 5, 10) is not redefined by enforcement tolerance, and `enforcement_threshold_speed` is not a substitute for the target. It is **not display hysteresis**: the small UI smoothing band around the target lives in `speed-reference` and threshold tuning, not here ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 11). It is **not jurisdictional law**: any jurisdiction profile is a configurable emulator / product profile, not a legal authority.

Feedback and enforcement **depends on speed reference and applicable candidate events, not on raw data or provider speed**. In POC V1, any feedback severity computed here is downstream of the event-applicability gate ([`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1, 11) and consumes the speed reference's target speed ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 4, 5, 10). Provider speed, ETA, traffic speed, segment speed, and posted-limit data are explicitly excluded from RoadAhead truth at the boundary level ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 8) and at the route-geometry level ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5, 6); they do not become feedback / enforcement truth by being routed through this area.

This area deliberately stops short of Canonizing exact tolerance values, exact tier boundary rules, exact `unsafe_likely` numeric formulas, exact pass-feedback hold duration, exact camera-risk visuals (pulse cadence, blink rules, camera-icon behavior), exact jurisdiction profile values (including any working Russia +20 km/h emulator profile), exact UI labels / colors / icons, exact display hysteresis values, exact current-speed smoothing, exact scenario test matrices, and implementation file / module layout. Those remain WIP / research / future Canon and will be settled by future implementation slices, ADRs, or Canon promotions once emulator validation supports promotion in the planned `feedback-and-enforcement`, `ui-model`, and `tuning-and-validation` work.

## Canon truths

The truths below are stable RoadAhead feedback-and-enforcement commitments. They are deliberately short and boundary-level; specific tolerance values, tier boundary rules, jurisdiction profiles, timing values, formulas, camera-risk visuals, and UI styling are explicitly **not** part of this area (see [Non-goals](#non-goals) and [Still WIP / not Canon](#still-wip--not-canon)).

1. **Feedback and enforcement is advisory severity semantics, not legal enforcement truth.** Feedback and enforcement is RoadAhead's anticipatory and post-pass severity feedback model. It is not a legal authority, not a violation claim, not a fine claim, not a confirmed-capture claim, and not a safety certification. This is a direct extension of [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truths 3, 4, and 5 at the feedback / severity level.

2. **Feedback and enforcement consumes the speed reference; it does not redefine the speed reference or the target speed.** Feedback severity is computed against the target speed exposed by the speed reference's `approach_target` state ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 4, 5). It does not replace, override, or augment that target speed. The speed-reference target remains the value driver-facing normal guidance is oriented around; this area only adds severity semantics on top of it.

3. **`target_speed_kmh` remains the guidance target; enforcement tolerance is a separate concept.** The event-derived target speed surfaced by the speed reference is what normal guidance bands and driver-facing UI orient around. Enforcement tolerance is a separately sourced severity buffer used by this area's feedback / severity computations only; it is not substituted for the target in any other area. This is a direct extension of [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 10 at the feedback / enforcement level.

4. **Enforcement tolerance is a configurable severity buffer used for feedback classification, not a legal claim.** Any `enforcement_tolerance` exposed by this area (regardless of representation — absolute, percentage, hybrid, or jurisdiction-specific) is a configurable severity-feedback parameter inside the product. It is not a legal threshold, not a regulatory authority, and does not constitute a claim about real-world enforcement behavior in any jurisdiction.

5. **An enforcement threshold derived from target speed plus resolved tolerance is a severity reference, not legal truth.** The product concept that an `enforcement_threshold_speed` can be derived from `target_speed_kmh` plus a `resolved_enforcement_tolerance_kmh` for use in severity / feedback classification is stable. This derivation is a severity reference, not a legal enforcement value, not a current-speed-limit authority, and not a substitute for the speed-reference target. The exact derivation rule (representation, fallback semantics, per-event-type applicability) remains tuning / implementation detail.

6. **`unsafe_likely` is a product severity signal, not a legal or safety certification.** The product concept that a pre-pass severity signal — for example, "the vehicle can no longer realistically reach the event at or below the configured severity threshold without unsafe / emergency-level braking" — is part of this area is stable at the principle level. It is a product severity indicator; it is not a legal verdict, not a safety certification, and not a guaranteed enforcement claim. The exact numeric formula, the comparator deceleration values, and any timing / hysteresis around it remain tuning / implementation detail.

7. **Pass feedback is a post-event feedback affordance based on how the event was passed, not a new speed source.** The temporary post-pass display / feedback state that confirms how the previous event was passed is a feedback affordance inside this area. It does not redefine the speed reference, does not introduce a new target-speed authority, and does not become a new speed-reference state ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 9). It uses the pass speed as observed against the target and the enforcement threshold; it does not supply a new speed truth.

8. **Pass-feedback tiers are severity categories, not violation / fine / capture verdicts.** Tiered post-pass feedback (the product concept of distinct severity categories such as Tier 0 / Tier 1 / Tier 2) is part of this area's severity language. The tier names communicate **how** the event was passed relative to the target and the severity threshold; they do not communicate that a violation occurred, that a fine will be issued, or that a camera captured the vehicle. The exact tier boundary rules, visual specifications, and wording are tuning / UI / implementation detail.

9. **Camera-risk feedback is a cautious event-specific feedback variant, not a confirmed camera capture or legal risk claim.** Camera-risk feedback is a semantic variant of pass feedback for camera-class events. Its meaning is bounded to "possible camera risk"; it must not assert violation, fine, confirmed capture, guaranteed enforcement, or any other anti-radar / enforcement-evasion semantics ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 3). The exact camera-risk visual behavior (camera icon, pulse / blink cadence, hold duration, color treatment) is implementation / UI / tuning detail.

10. **Display hysteresis is separate from enforcement tolerance and feedback severity.** The small UI smoothing band around `target_speed_kmh` (`display_hysteresis_kmh`) is UI smoothing in the speed-reference / threshold-tuning concern, not an enforcement tolerance and not a feedback severity. It does not change `target_speed_kmh`, does not change any enforcement threshold, does not change tier boundaries, and does not change `unsafe_likely` semantics. This is a direct extension of [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 11 at the feedback / enforcement level.

11. **Feedback and enforcement preserves candidate / non-verified semantics inherited from `event-data`, `event-applicability`, and `speed-reference`.** Because feedback / enforcement consumes the speed reference's target speed (sourced from prepared candidate events; [`../event-data/event-data.md`](../event-data/event-data.md) truths 1, 4, 5, 10 and [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 5, 13) and runs only on applicable candidates ([`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1, 11), feedback / severity outputs inherit candidate / non-verified status. Routing a target speed, a pass speed, a severity tier, or an `unsafe_likely` decision through this area does not upgrade it to verified, legally correct, or safety-certified truth.

12. **Jurisdiction profiles, including any Russia +20 km/h working profile, are configuration / emulator profiles, not legal truth.** Any named jurisdiction profile that supplies tolerance values to this area (including, at the time of this PR, the Russia-focused working POC default of +20 km/h) is a configurable emulator / product profile. It is not a legal authority, not legally verified by this Canon, and not a regulatory claim. Profile values remain working defaults and must be framed as such in product copy, UI, debug, and exports.

13. **Exact tolerance values, tier boundaries, timing, hold duration, camera-risk visuals, and jurisdiction rules are tuning / implementation details, not Canon in this area.** Exact `enforcement_tolerance_kmh`, exact `resolved_enforcement_tolerance_kmh` representations (absolute / percent / hybrid), exact `enforcement_threshold_speed` derivation formulas, exact Tier 0 / Tier 1 / Tier 2 boundary rules, exact `pass_feedback_hold_s`, exact pass-speed sampling rules, exact camera-icon pulse / blink cadence, exact `unsafe_likely` numeric formula, exact jurisdiction profile values (including Russia +20 km/h), exact UI labels / colors / icons, exact display hysteresis values, and exact current-speed smoothing are explicitly out of scope for this Canon area. They live in WIP / research, future implementation issues, future ADRs, or — once validated — future Canon work in this area, in `ui-model`, or in `tuning-and-validation`.

14. **Emulator evidence may inform future tuning, but does not automatically promote values to Canon.** Scenario sweep results, manual QA logs, and other emulator-produced evidence are valid inputs into future Canon / ADR review of feedback / enforcement values, but they do not by themselves promote a tolerance value, a tier boundary, a hold duration, a camera-risk visual, or a jurisdiction profile to Canon. Promotion still requires a deliberate Canon / ADR PR per [`../../README.md`](../../README.md) "Promotion rule", consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.

## Scope

This area covers:

- **Advisory severity feedback boundary** — the principle that feedback and enforcement is an advisory severity model, not a legal enforcement authority.
- **Consumption of speed-reference target** — the rule that feedback / severity is computed against the speed reference's target speed and consumes its outputs, not raw events or provider data.
- **Separation of target speed vs enforcement tolerance** — the rule that `target_speed_kmh` and `enforcement_tolerance` are separate concepts and that tolerance does not redefine the target.
- **Enforcement threshold as severity threshold, not legal threshold** — the rule that any enforcement threshold derived from target plus resolved tolerance is a severity reference, used inside feedback / severity computations only.
- **`unsafe_likely` as product severity signal** — the rule that `unsafe_likely` is a product severity indicator, not a legal verdict or safety claim, with exact numeric formulas remaining tuning detail.
- **Pass feedback as post-pass feedback affordance** — the rule that the temporary post-pass display / feedback state is a feedback affordance, not a new source of speed truth or a new speed-reference state.
- **Feedback tiers as severity categories** — the rule that tiered pass feedback (Tier 0 / Tier 1 / Tier 2 in current working language) is a severity category model, not a violation / fine / capture verdict.
- **Camera-risk feedback as cautious variant** — the rule that camera-risk feedback is a semantic variant of pass feedback for camera-class events, framed as "possible camera risk" only, with exact visual behavior left to implementation.
- **Separation from display hysteresis** — the rule that `display_hysteresis_kmh` is UI smoothing only and does not change enforcement tolerance, tier boundaries, or `unsafe_likely` semantics.
- **Candidate / non-verified inheritance** — the rule that feedback / severity outputs preserve the candidate / non-verified semantics inherited from upstream areas and do not become verified, legally correct, or safety-certified by being routed through feedback / enforcement.
- **Jurisdiction profile non-claim** — the rule that named jurisdiction profiles (including any Russia +20 km/h working profile) are configuration / emulator profiles, not legal truth or regulatory authority.
- **Exact-value deferral** — the rule that exact tolerance values, tier boundaries, timing, camera-risk visuals, jurisdiction rules, and `unsafe_likely` numerics remain WIP until validated.

## Product rules

These rules are normative. They follow from the Canon truths and constrain implementation, data behavior, UX, and product copy:

- **Do not label feedback as legal violation, fine, or confirmed camera capture.** Product copy, UI labels, debug strings, exports, and emulator UI must not present pass feedback, tier classifications, `unsafe_likely`, or camera-risk feedback as a legal violation, a fine, a ticket, a confirmed capture, or guaranteed enforcement. Camera-risk wording must remain "possible camera risk" only. (From truths 1, 8, 9; consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 3 and product rules.)

- **Do not use enforcement tolerance to redefine target speed.** The configurable severity buffer must not be substituted for `target_speed_kmh` inside the speed reference, inside normal guidance bands, inside the urgency model's deceleration computation, or in any other place that needs "the speed RoadAhead is orienting the driver around". Any enforcement threshold derived from target plus tolerance is a severity-only reference. (From truths 2, 3, 5; consistent with [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 10 and product rules.)

- **Do not use display hysteresis to redefine enforcement tolerance.** Display hysteresis is UI smoothing only. It must not be substituted for enforcement tolerance, must not move the enforcement threshold, must not move tier boundaries, and must not change `unsafe_likely` semantics. (From truth 10; consistent with [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 11.)

- **Feedback severity may compare current or pass speed to target plus configured tolerance, but this is a product severity threshold, not legal truth.** Comparisons of `current_speed_kmh` or `pass_speed_kmh` against `target_speed_kmh` and an `enforcement_threshold_speed` derived from target plus resolved tolerance are permitted inside this area's severity / feedback computations. They are product severity comparisons. They are not legal speed-limit comparisons and must not be framed as such anywhere downstream. (From truths 1, 4, 5, 8, 11.)

- **Pass feedback must be framed as how the driver passed the candidate event, not as a legal verdict.** Pass-feedback tier outputs — visuals, debug strings, exports, and any explanatory text — must describe the pass in terms of how it compared to the candidate event's target and the configured severity threshold, not in terms of legal consequence. (From truths 1, 7, 8, 11; consistent with [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truth 9.)

- **Camera-risk feedback must not imply confirmed camera detection, capture, or fine.** The camera-risk semantic variant of pass feedback must be framed as anticipatory and advisory only ("possible camera risk"); product copy and UI must not assert that a camera detected the vehicle, that a capture occurred, that a fine will be issued, or that enforcement is guaranteed. (From truths 1, 9; consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 3 and product rules.)

- **Jurisdiction profiles must be explicitly framed as configurable emulator / product profiles unless legally reviewed in future.** Any named jurisdiction profile (including any Russia-focused working profile) must be presented as a configurable emulator / product profile, not as a verified legal authority. If a future PR proposes to weaken this framing for a specific jurisdiction, it must do so through an explicit Canon / ADR PR after legal review. (From truths 1, 4, 12; consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) Still WIP / not Canon.)

- **Russia +20 km/h must remain a working profile / emulator configuration, not Canon legal truth.** The Russia +20 km/h POC default is a working emulator profile carried by [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md) §20.4 and discussed in [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md) §5.1, §11. It is not Canonized as a legal tolerance by this area and must not be promoted to legal truth without explicit legal review and a separate Canon / ADR PR. (From truths 1, 4, 12.)

- **Exact numeric values must remain WIP until validated.** No exact `enforcement_tolerance_kmh`, no exact `resolved_enforcement_tolerance_kmh` formula beyond principle-level separation, no exact `enforcement_threshold_speed` derivation beyond principle-level separation, no exact Tier 0 / Tier 1 / Tier 2 boundary, no exact `pass_feedback_hold_s`, no exact `unsafe_likely` formula, no exact camera-risk pulse / blink / icon cadence, and no exact jurisdiction profile value (including Russia +20 km/h) is Canonized by this area. Promotion requires emulator-based scenario evidence and a deliberate Canon / ADR PR per [`../../README.md`](../../README.md) "Promotion rule". (From truths 13, 14; consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.)

- **Debug output should show target, tolerance, resolved threshold, hysteresis, and feedback classification as distinct concepts where useful.** Emulator debug / QA surfaces that expose feedback / enforcement state should keep `target_speed_kmh`, `resolved_enforcement_tolerance_kmh`, `enforcement_threshold_speed`, `display_hysteresis_kmh`, and the feedback / severity classification (pass-feedback tier, camera-risk variant active, `unsafe_likely` state) as **separately inspectable** concepts. Collapsing them into a single field defeats the separation that this area Canonizes and would allow silent drift between concerns. Exact debug field names and surface layout remain implementation / tuning detail. (From truths 2, 3, 4, 5, 6, 10; consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 7, 8 and [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) implementation-facing implications.)

## Implementation-facing implications

These implications are intentionally high-level and stable. Concrete code, schema, debug, and UX shape belongs to future implementation slices or WIP / research:

- **Feedback / enforcement implementation should consume the speed reference and the current speed, not raw provider data or raw events.** The input to feedback / enforcement is the speed-reference state ([`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 4, 5, 6), the current speed (manually controlled in POC V1 per [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 6), and the active candidate's applicability status ([`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1, 11). Provider speed, ETA, traffic speed, posted-limit data ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5, 6), raw vendor source rows ([`../event-data/event-data.md`](../event-data/event-data.md) truths 2, 4), and non-applicable candidates must not flow into feedback / enforcement.

- **Feedback / enforcement may derive a severity threshold from target speed plus resolved tolerance, but target and threshold must remain separate in code and debug.** A derivation of the form `enforcement_threshold_speed = target_speed_kmh + resolved_enforcement_tolerance_kmh` is acceptable as a per-event, per-session computed severity reference. The two values must remain separately stored, separately inspectable, and separately displayed in any debug surface; collapsing them into a single field would break the separation rule (truths 2, 3, 5, 10).

- **UI layers may visualize severity, but visual details belong to `ui-model`.** Downstream UI layers (current-speed indicator, urgency ring, primary / secondary event circles, sign-like primitives, pass-feedback / camera-risk variants) may render the severity outputs of this area; how those outputs are visually presented — labels, colors, icons, ring intensity bands, blink / pulse cadences, layout — is owned by the planned `ui-model` area, not by this Canon.

- **Scenario sweeps should validate candidate values before any numeric promotion.** Scenario sweeps in the route-known web emulator ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 1, 4) over candidate tolerance values, tier boundary rules, hold durations, and `unsafe_likely` comparator deceleration values are valid inputs into future Canon / ADR review. They do not by themselves promote any value to Canon — that requires a deliberate Canon / ADR PR per [`../../README.md`](../../README.md) "Promotion rule" and consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.

- **Implementation slices needing exact values should cite WIP / research or future tuning-and-validation Canon — not this area.** This Canon area commits to feedback-and-enforcement principles, not to numbers, formulas, tier boundaries, jurisdiction values, or visual details. Slices that need such detail cite [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md), [`../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md`](../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md), [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md), [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), the planned `ui-model` / `tuning-and-validation` areas (once they exist), or a future ADR.

- **Feedback / enforcement state is per-session runtime, not base event truth.** The active enforcement profile, the resolved tolerance, the derived severity threshold, the active pass-feedback tier, the camera-risk variant flag, and the `unsafe_likely` state are session / runtime values, not properties of the base candidate event record ([`../event-data/event-data.md`](../event-data/event-data.md) truth 11). They must not be persisted onto the base event; persistence patterns (in-memory, per-session log, future replay artifact) are implementation detail.

## Still WIP / not Canon

The items below are deliberately **not promoted to Canon** in this PR. They remain WIP, research, or future-Canon candidates and are listed here so they cannot be mistaken for stable feedback-and-enforcement truth.

- **Exact enforcement profile schema** — the precise `enforcement_tolerance_profile` object shape, field names (`profile_id`, `label`, `country_or_region`, `tolerance_mode`, `absolute_kmh`, `percent`, `min_kmh`, `max_kmh`, `applies_to_event_types`, `status`, `legal_claim`, `notes`, `source` / `rationale`), defaults, and lifecycle. See [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md) §4, §5.
- **Exact tolerance type model: absolute / percent / hybrid** — whether tolerance is expressed as `absolute_kmh`, `percent`, hybrid, or some other representation, and the precise rules for resolving each mode. ## Related areas

- **[`product-boundary`](../product-boundary/product-boundary.md)** (existing Canon area) — what RoadAhead is and is not; legal / safety non-claims; external-data candidate boundary; route-provider geometry-only boundary; conservative posture under ambiguity. This `feedback-and-enforcement` area refines, at the feedback / severity level, the boundary-level commitments in `product-boundary` truths 3 (RoadAhead is not an anti-radar or enforcement-avoidance product; camera-related feedback is anticipatory and advisory), 4 (no legal speed-limit correctness claim), and 5 (no safety certification claim). The Russia +20 km/h profile remains a working configuration consistent with `product-boundary` Still WIP / not Canon and is not promoted to legal truth here.

- **[`validation-emulator`](../validation-emulator/validation-emulator.md)** (existing Canon area) — interactive web route emulator as POC V1 validation surface; route-known mode as the primary validation mode; deterministic manually controlled simulated speed; emulator debug visibility does not imply driver-facing display. This `feedback-and-enforcement` area assumes route-known mode and the manually controlled simulated current speed (`validation-emulator` truth 6) as the POC V1 inputs feeding pass-speed sampling and `unsafe_likely` evaluation, and it preserves the debug-vs-driver-facing distinction (`validation-emulator` truths 7 and 8) when severity state — active profile, resolved tolerance, derived threshold, tier classification, camera-risk variant flag, `unsafe_likely` state — is exposed in emulator debug. Promotion of any feedback / enforcement value still follows the emulator-evidence rule in `validation-emulator` truth 10.

- **[`route-geometry`](../route-geometry/route-geometry.md)** (existing Canon area) — route geometry as spatial reference; normalized provider boundary; provider speed / ETA / traffic / segment speed / posted limits explicitly excluded. The `pass_speed_kmh` sampling and the distance-to-event used by `unsafe_likely` and the urgency model consume route-geometry primitives (along-route position, route projection) downstream of `event-applicability`. Provider non-geometry signals must not be re-introduced as feedback / severity truth in this area (consistent with `route-geometry` truths 5 and 6).

- **[`event-data`](../event-data/event-data.md)** (existing Canon area) — external-source data policy; prepared normalized candidate events; source provenance preserved; route-specific derived fields are not part of the base event record. The target speed used for severity computation is sourced from a prepared candidate event ([`event-data` truths 1, 4, 5, 10](../event-data/event-data.md)); it carries the same candidate / non-verified status, which this area preserves in truth 11. Feedback / enforcement state is per-session runtime, not base event truth, consistent with [`event-data` truth 11](../event-data/event-data.md).

- **[`event-applicability`](../event-applicability/event-applicability.md)** (existing Canon area) — route / path applicability, direction applicability against the local route approach tangent, branch / intersection ambiguity handling, conservative suppression. Feedback states (`unsafe_likely`, pass-feedback tiers, camera-risk variant) are entered only after an applicable primary event is selected and passed; non-applicable candidates do not produce driver-facing feedback (`event-applicability` truths 1, 11).

- **[`speed-reference`](../speed-reference/speed-reference.md)** (existing Canon area) — active POC V1 speed modes (`unknown`, `approach_target`), target-speed semantics from the event itself, `provisional_limit` deferral, separation from enforcement tolerance, separation from display hysteresis, separation from pass-feedback severity. This `feedback-and-enforcement` area consumes the speed-reference target (`speed-reference` truths 4, 5) and preserves the strict separations established there (`speed-reference` truths 9, 10, 11): tolerance does not redefine the target (truth 3); the post-pass hold is not a new speed source (truth 7); display hysteresis stays separate (truth 10).
