# Validation Emulator

## Purpose

This area defines the **POC V1 validation surface**: an interactive web route emulator used to validate RoadAhead driver-facing event and urgency behavior before any Android overlay or mobile delivery work. It is the place where the boundary-level commitment in [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) — that POC V1 validates driver-facing behavior in a web emulator before Android overlay work — is refined into a stable, citable area of Product Canon.

The emulator is a **first-class product / testing artifact**, not a throwaway toy. It is **not** the eventual delivery surface. Decisions about delivery — Android standalone, Android overlay on top of an existing navigator, mobile UX, permissions, lifecycle — are out of scope here and remain WIP / future Canon. This area only commits to the validation surface itself: what it exists for, what role it plays, and what it is explicitly not.

## Canon truths

The truths below are stable RoadAhead validation-surface commitments. They are deliberately short and surface-level; specific algorithms, schemas, providers, UI shape, debug fields, and tuning numbers are explicitly **not** part of this area (see [Non-goals](#non-goals) and [Still WIP / not Canon](#still-wip--not-canon)).

1. **POC V1 validation starts with an interactive web route emulator.** The first POC V1 validation environment is an interactive web route emulator. It is the surface on which the three-circle anticipatory road-understanding behavior is iterated and reviewed before any mobile / overlay work is undertaken.
2. **The emulator validates driver-facing event and urgency behavior before Android overlay or standalone Android prototype work.** POC V1 staging is **Phase 0 — interactive web route emulator** first; Android standalone prototype and Android overlay on top of an existing navigator are deferred and not part of POC V1 implementation scope.
3. **The emulator is a deliberate product / testing artifact, not a throwaway toy, but it is also not the eventual delivery surface.** It is designed and reviewed as a product/testing artifact for behavioral validation. It is not a navigator, not a driver-facing mobile product, and not the surface on which RoadAhead is eventually delivered to drivers. Decisions that hold inside the emulator do not automatically hold for a future delivery surface.
4. **Route-known mode is the primary POC V1 validation mode.** The emulator validates RoadAhead behavior on an explicit, known route geometry (planned route, imported track, or manually authored polyline). Route-known mode is the surface that POC V1 actually exercises.
5. **Route-unknown / no-route mode is future strategy only, not POC V1 implementation scope.** Route-unknown behavior — including free-map movement, branch-prediction without a route, and ambiguity heuristics without route geometry — is intentionally out of POC V1 validation scope. It may inform future product work but does not constrain POC V1.
6. **The emulator may simulate route progress and use deterministic, manually controlled vehicle speed.** To make validation repeatable and reviewable, the emulator may move a simulated vehicle along the known route and use deterministic, manually controlled simulated speed; provider speed, ETA, traffic speed, or segment speed are not used as RoadAhead speed truth (consistent with the route-provider boundary in the [`product-boundary`](../product-boundary/product-boundary.md) area). The exact UI mechanics, input controls, and timing are not part of this Canon truth.
7. **The emulator may expose richer debug and tuning information than the future driver-facing surface.** As a validation artifact, the emulator may surface internal state — direction-applicability decisions and reasons, route-projection state, urgency-state computation, active enforcement profile, active tuning values, and similar — that would be inappropriate or distracting on a driver-facing surface. The presence of such debug visibility in the emulator is a property of the validation surface, not of the future product.
8. **Emulator-visible debug data does not imply driver-facing display.** The fact that the emulator shows an internal state, a suppressed candidate, a configuration value, or a debug field does not promote that field to driver-facing UI for any future delivery surface. Driver-facing eligibility is a separate, deliberate decision and belongs to other areas.
9. **Candidate external event data may be used for emulator validation, but remains candidate input, not verified truth.** Datakam / OpenSpeedcam-derived candidate events and any other external candidate data may be loaded into the emulator for validation scenarios. As stated in the [`product-boundary`](../product-boundary/product-boundary.md) area, they remain `ExternalObservation` candidate inputs in the emulator just as they do anywhere else; the emulator must not surface them — visually or in debug — as confirmed, verified, or legally correct.
10. **The emulator validates behavior and product assumptions; it does not itself Canonize tuning values, provider choices, event algorithms, or legal claims.** Running a scenario in the emulator does not promote a route provider, an event-applicability heuristic, a feedback timing, a tuning value, or any legal / enforcement claim to Canon. Promotion of any such value still requires a deliberate Canon / ADR PR with recorded evidence (per [`../../README.md`](../../README.md) "Promotion rule").

## Scope

This area covers:

- **The web emulator as POC V1 validation surface** — its existence, its role as the first-class POC V1 validation environment, and its status as a deliberate product/testing artifact rather than a throwaway toy.
- **Route-known validation mode as the primary POC V1 validation mode** — the commitment that POC V1 exercises RoadAhead on an explicit, known route geometry first, with route-unknown / no-route mode out of POC V1 scope.
- **Simulated route progress / speed control at the principle level** — the principle that the emulator may move a simulated vehicle along the known route and use deterministic, manually controlled simulated speed for repeatable validation; exact UI affordances, control schemes, and timing are not committed here.
- **Debug / tuning visibility as validation support** — the principle that the emulator may surface richer internal state, configuration, and tuning visibility than a driver-facing surface would, because it is a validation artifact.
- **Separation between emulator-visible debug and driver-facing UI** — the principle that emulator debug visibility does not imply driver-facing eligibility on any future delivery surface.
- **Relation to the `product-boundary` Canon area** — this area refines, at the validation-surface level, the boundary-level commitment in [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) (truth 7) that POC V1 validates driver-facing behavior in a web route emulator before Android overlay work and that the emulator is not the eventual delivery surface.

## Product rules

The rules below are normative product rules derived from the [Canon truths](#canon-truths). They constrain how POC V1 work is sliced, how the emulator is positioned, and how emulator outputs are consumed.

- **POC V1 implementation slicing should start from emulator behavior, not Android overlay.** Implementation work for POC V1 targets the interactive web route emulator first; Android standalone prototype and Android overlay tickets are deferred until emulator behavior has been validated. (From truths 1, 2, 3.)
- **Emulator design must support route-known validation first.** Any first-slice emulator design must support route-known mode (known route geometry from planning, file import, or manual polyline) before optimizing for any route-unknown / no-route scenario. Route-unknown / no-route exploration is future strategy, not POC V1 implementation scope. (From truths 4 and 5.)
- **The emulator may include controls and debug panels that would be inappropriate for driver-facing mobile UX.** Because the emulator is a validation artifact and not a delivery surface, it may include speed-control affordances, brake-to-target controls, scenario sweep controls, configuration toggles, and debug panels that would be unsafe or distracting on a driver-facing mobile surface. The emulator's UI shape is not constrained by future driver-facing UX constraints. (From truths 3, 6, 7.)
- **Debug visibility must not be mistaken for driver-facing eligibility.** Any internal state, suppressed candidate, configuration value, or computed field visible in the emulator's debug surface is debug-level only. It is not automatically promoted to driver-facing UI on any future delivery surface; that decision belongs to other areas. (From truths 7 and 8.)
- **Emulator fixtures and candidate data must preserve candidate / non-truth labeling.** Datakam / OpenSpeedcam-derived candidate events and any other external candidate data loaded into the emulator must be surfaced as candidate observations, not as confirmed / verified / legally-correct events — both in the emulator UI and in the debug / export surfaces. (From truth 9 and the [`product-boundary`](../product-boundary/product-boundary.md) data-truth rule.)
- **Scenario sweeps may use the emulator to generate validation evidence, but evidence must be recorded before tuning values become Canon.** Tuning values (thresholds, hysteresis, timings, deceleration profiles, reaction times, lookahead caps) and safety-sensitive UX rules require validation evidence — scenario sweep results, manual QA, or other recorded results — before Canon promotion. A number stays WIP until measured and recorded. (From truth 10 and the [`../../README.md`](../../README.md) "Promotion rule".)
- **Android-specific assumptions must not be inferred from emulator-only behavior.** Conclusions justified only by "the emulator does it this way" do not transfer to a future Android standalone prototype or overlay. Android permissions, lifecycle, overlay UX, performance, and platform behavior will be re-evaluated when their own Canon areas are added. (From truths 2, 3, 8.)

## Implementation-facing implications

The implications below are intentionally high-level and stable. Concrete code, data, debug, and UX shape belongs to the more specific area / WIP / research docs they cite.

- **Implementation issues for POC V1 should target web emulator behavior before mobile / overlay work.** Issue / PR scoping under Issue #21 (and future implementation tickets that consume it) should treat the web emulator as the first execution surface; Android-standalone and Android-overlay scope is deferred until after emulator-level behavior is validated.
- **The emulator should make relevant internal state inspectable for QA / tuning, but Product Canon for specific debug fields belongs in more specific areas.** This Canon area commits only to the principle that the emulator may expose richer debug / tuning visibility than a driver-facing surface; concrete debug field lists (e.g., direction-applicability fields, urgency-state fields, enforcement-profile fields, tuning-config fields) belong in the relevant area's Canon doc when promoted, or in WIP / research until then.
- **Any route geometry, event data, applicability, feedback, or tuning implementation should cite the relevant area / WIP / research doc, not this Canon area.** This area does not name a route provider, an event store engine, an event applicability algorithm, a feedback timing, a tuning value, or a debug field. Slices that need such detail cite the appropriate area's Canon doc (when it exists) or the relevant WIP / research doc (when the area is still WIP).
- **Emulator validation outputs can inform future Canon / ADR, but do not automatically promote values to Canon.** Scenario sweep results, manual QA logs, and other emulator-produced evidence are valid inputs into future Canon / ADR review. They do not by themselves promote a tuning value, a provider choice, an event-applicability heuristic, or a feedback timing to Canon — that still requires a deliberate Canon / ADR PR per the [`../../README.md`](../../README.md) "Promotion rule".

## Related areas

The areas below are the planned Canon areas listed in [`../README.md`](../README.md). At the time of this PR, only `product-boundary` and `validation-emulator` exist as Canon docs; the other planned areas are not yet Canon. Per the area README rules ("do not pre-link to areas that have not been created"), planned-but-not-created areas are referenced by name and routed through [`../README.md`](../README.md), not by direct path.

- **[`product-boundary`](../product-boundary/product-boundary.md)** (existing Canon area) — what RoadAhead is and is not, legal / safety non-claims, external-data candidate boundary, route-provider geometry-only boundary, conservative posture under ambiguity. This validation-emulator area refines the boundary-level commitment that POC V1 validates driver-facing behavior in a web route emulator before Android overlay work and that the emulator is not the eventual delivery surface (`product-boundary` truth 7).
- **`route-geometry`** (planned; not yet a Canon area) — provider-supplies-geometry-only contract, normalized route polyline / projection / tangent / route-position utilities. Provides the specific mechanics behind the emulator's route-known mode; does not change the validation-surface commitments here. See planning entry in [`../README.md`](../README.md).
- **`event-data`** (planned; not yet a Canon area) — external-source data policy, raw-data-import-only rule, prepared normalized candidate event shape, future `VerifiedRoadEvent` boundary. Provides the specific data-shape that the emulator loads as candidate inputs (truth 9). See planning entry in [`../README.md`](../README.md).
- **`event-applicability`** (planned; not yet a Canon area) — route / path applicability, direction applicability against the local route approach tangent, branch / intersection ambiguity handling, conservative suppression. Provides the specific selection mechanics whose decisions the emulator validates and exposes in debug. See planning entry in [`../README.md`](../README.md).
- **`speed-reference`** (planned; not yet a Canon area) — active POC V1 modes (`unknown`, `approach_target`), target-speed semantics from the event itself, `provisional_limit` deferral, manually controlled simulated speed in POC V1. Provides the specific state-machine that the emulator drives during validation. See planning entry in [`../README.md`](../README.md).
- **`feedback-and-enforcement`** (planned; not yet a Canon area) — pass-feedback tiers, camera-risk variant, configurable `enforcement_tolerance` severity buffer (not a legal claim), strict separation between `target_speed`, `enforcement_tolerance`, and `display_hysteresis_kmh`. Provides the feedback / enforcement details that the emulator exposes for validation but does not Canonize via this area. See planning entry in [`../README.md`](../README.md).
- **`ui-model`** (planned; not yet a Canon area) — three-circle UI, primary / secondary event roles, visual states, sign-like primitives, POC V1 horizontal-only layout. Provides the specific UI shape that the emulator renders; the emulator may surround that UI with debug / control affordances that the UI model itself does not include. See planning entry in [`../README.md`](../README.md).
- **`tuning-and-validation`** (planned; not yet a Canon area) — threshold tuning, scenario sweep methodology, validation evidence required before promoting a tuning value to Canon, what remains WIP until measured. This is the area that, when it is promoted, will Canonize the methodology by which emulator-produced evidence becomes a Canon-promotable tuning value (truth 10). See planning entry in [`../README.md`](../README.md).
