# Event Applicability

## Purpose

This area defines RoadAhead's stable product boundary for **deciding whether a candidate event applies to the current route / path / direction** in POC V1.

Event applicability is the **driver-facing eligibility gate**: a candidate event must pass applicability checks before it is selected for driver-facing display, urgency computation, or feedback. RoadAhead must not surface an event to the driver merely because it is geographically nearby on a map — the question applicability answers is "does this event apply to the path I am actually following, in the direction I am actually approaching from?", not "is there an event somewhere in my vicinity?".

In POC V1, applicability is evaluated **route-known first**: the route-known interactive web route emulator ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 4) is the primary surface on which applicability is exercised, and the normalized route geometry contract ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truth 4) is the spatial reference. Route-unknown / no-route applicability is future strategy, not POC V1 scope ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 5).

This area refines the conservative-ambiguity posture established at the boundary level ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 9): when route / path / direction applicability cannot be determined with confidence, driver-facing behavior **prefers suppression over confident display**. Suppressed candidates remain inspectable in emulator debug / QA surfaces, but debug visibility does not imply driver-facing eligibility ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 7 and 8).

This area deliberately stops short of Canonizing exact thresholds, exact route projection or local tangent algorithms, exact source-direction interpretation rules, exact branch / ambiguity heuristics, exact suppression-reason enums, exact debug field lists, and the no-route / route-unknown strategy. Those remain WIP / research and will be settled by future implementation slices, ADRs, or Canon promotions once emulator validation supports promotion.

## Canon truths

The truths below are stable RoadAhead event-applicability commitments. They are deliberately short and boundary-level; specific algorithms, thresholds, formulas, source-direction interpretation rules, branch heuristics, suppression-reason enums, debug field lists, route-cache schemas, and no-route strategies are explicitly **not** part of this area (see [Non-goals](#non-goals) and [Still WIP / not Canon](#still-wip--not-canon)).

1. **Candidate events must pass applicability checks before driver-facing display or feedback.** Applicability is a deliberate gate in front of the driver-facing surface: urgency computation, primary / secondary event selection (WIP spec §8.1, §8.2), three-circle UI rendering, and pass / camera-risk feedback may only operate on candidates that have passed this gate.

2. **Geographic proximity alone is insufficient for driver-facing applicability.** Nearest-point lookup, bounding-box selection, or a simple distance radius are **not** by themselves applicability decisions. A candidate that is geographically near the vehicle but does not apply to the current path / direction must not be surfaced to the driver, even when it would otherwise be the nearest event.

3. **POC V1 event applicability is route-known first.** The primary POC V1 applicability surface is route-known mode in the interactive web route emulator. Route-unknown / no-route applicability is future strategy only and is not part of POC V1 implementation scope (consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 4 and 5).

4. **Route geometry is the spatial reference for applicability evaluation.** Applicability in route-known mode is evaluated against the normalized route geometry contract established by [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) (truth 4), not against the global map alone. The route polyline, the route projection of a candidate, the along-route position of the vehicle, the along-route position of the event, and the local route approach tangent are the spatial primitives applicability relies on.

5. **Applicability is evaluated against the current route / path, not against the global map alone.** The product question applicability answers is "does this candidate event apply to the path the vehicle is currently or assumedly following?". A candidate that is correctly placed on the map but does not belong to the vehicle's current route — for example, on a parallel carriageway, on a different branch at a fork, on a frontage / service road, or on the opposite direction of a divided road — does not become driver-facing simply because it is on the map.

6. **Applicability depends on both route position and direction / approach compatibility.** A candidate must be ahead of the vehicle along the route **and** its direction / approach interpretation must be compatible with how the vehicle is approaching the event. Position alone is insufficient (a wrong-direction event ahead must not be confidently shown); direction alone is insufficient (a same-direction event off the route must not be confidently shown).

7. **The local route approach tangent is the product-level reference for direction compatibility in route-known mode.** Direction compatibility is evaluated against the **local route approach tangent** near the event (the bearing of the route polyline as the vehicle approaches the event), not against the vehicle's instantaneous current heading. The vehicle's instantaneous heading is dominated by curves, jitter, and short-segment noise; the approach tangent represents the direction the vehicle would actually be travelling as it reaches the event. The exact tangent computation (window length, weighting, fallbacks) is implementation detail.

8. **Source direction fields such as Datakam `DIRECTION` / `DIRTYPE` are candidate source metadata, not verified truth.** Datakam `DIRECTION`, `DIRTYPE`, and equivalent source-direction fields are external candidate signals carried through normalization for use by the applicability evaluation. They are not asserted to be globally correct, are not legally authoritative, and must not be hard-coded into product logic as global truth. This is a direct extension of [`../event-data/event-data.md`](../event-data/event-data.md) truths 1, 5, 8 and [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 6.

9. **Bidirectional, unknown, and unclear source direction semantics must be handled conservatively.** When source direction metadata indicates bidirectional applicability, when it is missing, when it is unclear, or when its interpretation is not understood (for example, anomalous or rare `DIRTYPE` values), the applicability evaluation must take a conservative driver-facing posture — bidirectional candidates are accepted in either approach orientation only when other applicability checks support it; unknown / unclear semantics default to suppression on doubt. The exact interpretation rules (per-`DIRTYPE` semantics, `(DIRECTION + 180) mod 360` handling, source-specific overrides) are implementation detail and remain WIP.

10. **Branches, ramps, parallel carriageways, T-junctions, intersections, and competing projections are ambiguity sources for route-known applicability.** Real road geometry produces situations in which a candidate event's projection onto the route polyline cannot be confidently attributed to the vehicle's chosen route branch — for example, when a parallel carriageway, frontage road, or off-ramp lies close enough that the candidate could plausibly belong to either, or when the event is inside a junction zone where the chosen branch is geometrically distinct but the candidate coordinate is offset enough to compete. These are known ambiguity classes that applicability evaluation must consider.

11. **When route / path / direction applicability is ambiguous, driver-facing behavior must prefer suppression / non-claim over confident display.** This is a direct extension of [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 9 at the event-applicability level: it is better to not show a candidate than to confidently show one from the wrong road, wrong branch, opposite carriageway, or wrong direction. The cost of a false positive (a wrong-road or wrong-direction event surfaced to the driver) is higher than the cost of a false negative (a missed display), particularly in safety-sensitive UX.

12. **Suppressed and ambiguous candidates may remain visible in emulator debug / QA surfaces, but debug visibility does not imply driver-facing eligibility.** Applicability evaluation must preserve enough information about suppression — including the reasons a candidate was suppressed or flagged ambiguous — so that decisions are inspectable for QA and tuning purposes. This debug visibility is a property of the validation surface ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 7 and 8), not a license to promote the same fields to a future driver-facing surface.

13. **Route-specific applicability results are derived per route / session and are not base event truth.** The result of applicability evaluation against a specific route (projection distance, along-route position, direction delta, approach tangent value, branch-ambiguity state, applicability decision, suppression reasons) is valid only for that route. These values are computed per route or stored in route-specific cache structures keyed on the route. They must not be persisted onto the base event record. This is a direct extension of [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truth 4 / implementation-facing implications and [`../event-data/event-data.md`](../event-data/event-data.md) truth 11.

14. **Exact applicability thresholds, formulas, source-direction interpretation rules, branch heuristics, and the no-route strategy are tuning / implementation details, not Canon in this area.** Exact projection accept / warn / reject distances, exact direction-delta thresholds, exact approach-window length, exact branch-zone radius, exact projection-competitor delta, exact heading-competitor delta, exact distance / time lookahead caps, exact tangent computation formulas, exact Datakam `DIRECTION` / `DIRTYPE` interpretation tables, and the exact route-unknown / no-route applicability strategy are explicitly out of scope for this Canon area. They live in WIP / research, future implementation issues, future ADRs, or — once validated — future Canon work.

## Scope

This area covers:

- **Applicability as a driver-facing eligibility gate** — the principle that applicability is evaluated before driver-facing display / feedback, and the rule that geographic proximity alone is insufficient for driver-facing applicability.
- **Route-known POC V1 applicability boundary** — the rule that POC V1 evaluates applicability in route-known mode against the normalized route geometry contract; route-unknown is future strategy only.
- **The distinction between "nearby" and "applicable"** — the rule that nearest-point lookup, bounding-box selection, or a distance radius are not by themselves applicability decisions for driver-facing purposes.
- **Route / path position principle** — the rule that applicability is evaluated against the current route / path, not against the global map alone; same-map candidates on parallel carriageways, branches, ramps, or opposite directions are not automatically driver-facing.
- **Direction / approach compatibility principle** — the rule that applicability requires both along-route position and direction / approach compatibility, not one or the other.
- **Local route approach tangent at the principle level** — the rule that, in route-known mode, the local route approach tangent near the event is the product-level reference for direction compatibility, not the vehicle's instantaneous current heading.
- **Source direction metadata as candidate / unverified** — the rule that Datakam `DIRECTION` / `DIRTYPE` and equivalent source fields are external candidate signals, not verified truth, and must not be hard-coded as global truth.
- **Ambiguity classes at the principle level** — the recognition that branches, ramps, parallel carriageways, T-junctions, intersections, projection competitors, and bidirectional / unknown source direction semantics are real applicability ambiguity sources that the route-known model must handle.
- **Conservative suppression posture** — the rule that ambiguous applicability defaults to suppression / non-claim in the driver-facing surface, consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 9.
- **Debug vs driver-facing distinction** — the rule that suppressed / ambiguous candidates may remain visible in emulator debug / QA surfaces, but debug visibility does not imply driver-facing eligibility.
- **Route-specific derived applicability data boundary** — the rule that route-specific applicability results (projection, tangent, direction delta, decision, suppression reasons) are per-route / per-session derived values and are not base event truth.

## Product rules

These rules are normative. They follow from the Canon truths and constrain implementation, data behavior, and UX:

- **Do not select a candidate event for driver-facing display solely because it is nearest or within a distance radius.** Geographic proximity, bounding-box membership, and nearest-point lookup are not by themselves applicability decisions. The applicability gate must run before driver-facing selection. (From truths 1, 2.)

- **In route-known POC V1, evaluate candidate events against the current route geometry.** Applicability evaluation in POC V1 runs against the normalized route geometry contract from [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md). Route-unknown / no-route applicability is future strategy only and must not be implied by POC V1 behavior. (From truths 3, 4.)

- **Applicability must consider both along-route position and direction / approach compatibility.** A candidate must be ahead of the vehicle along the route and direction / approach compatible. Neither alone is sufficient for driver-facing eligibility. (From truths 5, 6.)

- **Use the local route approach tangent as the product-level direction reference in route-known mode, not the vehicle's instantaneous current heading.** Direction compatibility checks must reference the bearing of the route polyline as the vehicle approaches the event, not the vehicle's instantaneous heading, which is dominated by curves and short-segment noise. (From truth 7.)

- **Treat source direction data as unverified candidate metadata.** Datakam `DIRECTION` / `DIRTYPE` and any equivalent source direction fields are candidate signals carried through normalization. They must not be hard-coded as global truth in product logic; their interpretation is configurable and revisable. (From truth 8.)

- **If source direction conflicts with route geometry, do not confidently display the event driver-facing by default.** When the source direction interpretation produces a direction-applicability conflict against the local route approach tangent, the default driver-facing posture is suppression. The candidate may remain visible in debug; a future curated-override mechanism is out of POC V1 scope. (From truths 8, 9, 11; consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 9.)

- **If bidirectional, unknown, or unclear source direction semantics apply, take a conservative driver-facing posture.** Bidirectional candidates are accepted in either approach orientation only when other applicability checks support it; unknown or unclear semantics default to suppression on doubt. Exact per-`DIRTYPE` rules and source-specific interpretation tables remain WIP. (From truths 8, 9, 11.)

- **If branch, ramp, parallel-carriageway, T-junction, or intersection ambiguity prevents confident attribution of a candidate to the vehicle's route branch, suppress or keep debug-only.** Route-known mode resolves the route branch geometrically, but a candidate can still be ambiguous if its projection plausibly belongs to a competing nearby segment. Ambiguous candidates default to suppression in the driver-facing surface; they may remain visible in debug. (From truths 10, 11.)

- **Preserve suppressed candidates and the reasons they were suppressed in emulator debug / QA surfaces where useful.** Suppression must be inspectable so the applicability behavior is auditable and tunable. The exact set of reason codes and debug fields is implementation detail. (From truth 12; consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 7, 8.)

- **Do not promote emulator-visible suppression / debug fields to driver-facing UI without a deliberate UI / driver-facing decision.** Debug visibility is a property of the validation surface; driver-facing eligibility is a separate decision and belongs to other areas (planned `ui-model`, `feedback-and-enforcement`). (From truth 12.)

- **Store applicability results as route / session-derived values, not base event fields.** Route-projection distance, along-route position, projected segment index, local route approach tangent, direction delta, branch-ambiguity state, applicability decision, and suppression reasons must be computed per route or stored in route-specific cache structures. They must not be persisted as canonical properties of the base event. (From truth 13; consistent with [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) and [`../event-data/event-data.md`](../event-data/event-data.md) truth 11.)

- **Keep exact thresholds, formulas, source-direction interpretation rules, branch heuristics, suppression-reason enums, debug field lists, route-cache schemas, and the no-route strategy in WIP / tuning until validated.** No exact numeric value, no exact formula, and no exact enumeration is Canonized by this area. Promotion of any such value requires emulator-based scenario evidence and a deliberate Canon / ADR PR per [`../../README.md`](../../README.md) "Promotion rule". (From truth 14; consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.)

## Implementation-facing implications

These implications are intentionally high-level and stable. Concrete code, schema, debug, and UX shape belongs to future implementation slices or WIP / research:

- **Future event-applicability implementation should use a pipeline / staged eligibility model.** Candidate ingestion and base event data are not enough; route-specific applicability is a separate evaluation step that runs after candidate preparation and consumes the normalized route geometry. The exact step ordering, fields, and accept / warn / suppress contract per step are implementation detail; see [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md) §3 for the current draft pipeline.

- **The emulator should expose enough debug information to review why a candidate was accepted, flagged, or suppressed, but the exact debug field list remains WIP.** This Canon area commits to the principle that suppression must be inspectable; concrete debug field names, the suppression-reason enum, and the debug surface schema belong in the relevant WIP / research doc until validated and promoted.

- **Event-applicability implementation should consume normalized route geometry and prepared candidate events, not raw provider / source objects.** Applicability evaluation references the normalized `RouteGeometry` contract ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truth 7) and the prepared normalized candidate events ([`../event-data/event-data.md`](../event-data/event-data.md) truth 4); it must not depend on provider-specific route objects or on raw vendor source rows.

- **Route-specific applicability / cache values should be invalidated when route geometry or interpretation rules change.** When the route changes, the route-derived applicability values are no longer valid and must be recomputed for the new route. When the source-direction interpretation rule changes (for example, a future revision of the `(DIRECTION + 180) mod 360` working assumption, or a new source with different semantics), derived bearings and direction deltas must be invalidated. The exact mechanism (in-memory only, per-session cache, future keyed table) is implementation detail; see [`../../../research/roadahead-prepared-event-store-recommendation.md`](../../../research/roadahead-prepared-event-store-recommendation.md) §5.4, §7, §8.3.

- **Implementation slices that need precise applicability thresholds, projection / tangent algorithms, branch heuristics, suppression-reason enums, debug field lists, or route-cache schemas should cite the relevant research doc — not this Canon area.** This area commits to event-applicability principles, not to algorithms, thresholds, or enums. Slices that need such detail cite [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md), [`../../../research/roadahead-route-geometry-provider-recommendation.md`](../../../research/roadahead-route-geometry-provider-recommendation.md), [`../../../research/roadahead-prepared-event-store-recommendation.md`](../../../research/roadahead-prepared-event-store-recommendation.md), [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), or a future Canon / ADR.

- **Emulator-produced evidence does not automatically promote thresholds or pipeline steps to Canon.** Scenario sweep results that exercise applicability (the direction applicability recommendation §7 and the threshold tuning recommendation §10 enumerate the scenario classes) are valid inputs into future Canon / ADR review. They do not by themselves promote a threshold, a tangent algorithm, a branch heuristic, or a suppression-reason enum to Canon — that still requires a deliberate Canon / ADR PR per the [`../../README.md`](../../README.md) "Promotion rule" and consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.
