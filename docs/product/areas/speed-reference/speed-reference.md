# Speed Reference

## Purpose

This area defines RoadAhead's stable product boundary for the **speed reference** used by POC V1 driver-facing behavior.

The speed reference is the **current product state that says what speed value, if any, RoadAhead is orienting the driver around** — what target the current-speed indicator is comparing the vehicle's speed against, or that there is no such target right now. It exists so that the driver-facing surface can answer a single, deliberately narrow question — *is RoadAhead orienting the driver around some speed at this moment, and if so which one?* — without that question being silently entangled with legal correctness, enforcement severity, UI smoothing, or post-pass feedback.

The speed reference is **not legal truth**: it does not assert that any value it carries is the legally valid speed limit at the vehicle's current location. It is **not enforcement tolerance**: the configurable severity buffer used for `unsafe_likely`, pass-feedback tiers, and camera-risk feedback is a separate concept, not a redefinition of the target. It is **not display hysteresis**: the small UI smoothing band that prevents flicker around the target is a separate concept, not a redefinition of the target. It is **not pass-feedback severity**: the temporary post-pass visual state is a feedback affordance, not a new source of speed truth.

The speed reference **depends on applicable candidate events, not on raw data or provider speed**. In POC V1, any target the speed reference exposes is derived from a RoadAhead candidate event that has already passed the route / path / direction applicability gate established by [`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md). Provider speed, ETA, traffic speed, segment speed, and posted-limit data are explicitly excluded from RoadAhead truth at the boundary level ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truths 4, 8 and [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5, 6); they do not become speed truth by being routed through the speed reference.

This area deliberately stops short of Canonizing the exact speed-reference state machine, exact state names beyond stable concepts, exact `provisional_limit` behavior, exact `recent_passed_speed_candidate` behavior, exact pass-feedback hold duration, exact current-speed smoothing, exact display hysteresis value, exact enforcement tolerance value, exact feedback tiers, exact camera-risk feedback, exact Russia +20 km/h profile, exact UI label / color / icon behavior, exact test scenarios, and implementation file / module layout. Those remain WIP / research / future Canon and will be settled by future implementation slices, ADRs, or Canon promotions once emulator validation supports promotion.

## Canon truths

The truths below are stable RoadAhead speed-reference commitments. They are deliberately short and boundary-level; specific state machines, threshold values, timing values, smoothing formulas, feedback tiers, jurisdiction profiles, and UI styling are explicitly **not** part of this area (see [Non-goals](#non-goals) and [Still WIP / not Canon](#still-wip--not-canon)).

1. **Speed reference is a product state used for guidance context, not a legal assertion.** Speed reference is RoadAhead's current driver-facing answer to the narrow question "what speed, if any, is the system orienting the driver around right now?". It is anticipatory guidance context, not a legal speed-limit authority, not a violation claim, and not a safety certification. This is a direct extension of [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truths 4 and 5.

2. **POC V1 speed reference is derived from applicable RoadAhead candidate events, not from provider speed / ETA / traffic / posted-limit outputs.** Any target speed the speed reference exposes in POC V1 is sourced from a prepared RoadAhead candidate event that has passed event applicability (e.g., a `speed_limit` event's posted speed, a `road_bump` event's advisory slowdown speed, a `static_camera` event's posted speed). Provider speed, ETA, traffic speed, segment speed, and posted-limit data are explicitly excluded from RoadAhead truth ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 8; [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5 and 6) and must not become speed-reference truth by being routed through this area.

3. **`unknown` is a valid speed-reference state when RoadAhead has no applicable target speed.** When no applicable speed-related event is currently driving driver-facing guidance, the correct speed-reference state is `unknown` — meaning RoadAhead is explicitly not orienting the driver around any specific target. `unknown` is not a failure mode; it is the honest product answer when no candidate event applies and the system therefore makes no target claim. This is the natural consequence of the conservative-suppression posture in [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 9.

4. **`approach_target` is the main active POC V1 speed-reference state when an applicable speed-related event provides a target.** When an applicable speed-related candidate event is the active primary event and it carries an event-derived target speed, the speed reference is `approach_target`, with the event's target as the current target speed. `approach_target` is the only active POC V1 speed-reference state that orients driver-facing guidance around a specific value; `unknown` is the only other active state.

5. **`target_speed_kmh` is event-derived candidate guidance context, not legal speed-limit truth.** The target speed exposed by an `approach_target` speed reference is a property of the candidate event from which it was sourced (e.g., the event's posted / recommended / advisory speed, such as Datakam `SPEED`). It is candidate guidance context — useful for anticipatory speed guidance — not a legal speed-limit authority. Source candidate-data semantics from [`../event-data/event-data.md`](../event-data/event-data.md) (truths 1, 5, 10) and the non-claims in [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) (truths 4, 6) carry through unchanged.

6. **Speed reference is evaluated only after event applicability has selected an eligible candidate.** The speed reference is a downstream consumer of the event-applicability gate, not a separate route into the driver-facing surface. A candidate event that has not passed event applicability — including a wrong-direction, branch-ambiguous, or otherwise non-applicable candidate — must not drive `approach_target` or supply a target speed. This is a direct extension of [`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1 and 11 at the speed-reference level.

7. **`provisional_limit` is deferred and not active POC V1 Canon.** A `provisional_limit` mode — in which RoadAhead would treat a speed as the current road-segment speed reference based on a confirmed sign pass, settlement boundary, validity rule, or trusted segment-level data — is preserved as a future product concept. It is **not** an active POC V1 speed-reference state, because POC V1 has no reliable source of current road-segment speed truth and must not behave as if it knows the current legal speed limit after passing a sign. The exact conditions, sources, and lifecycle a future `provisional_limit` would require remain WIP / future Canon.

8. **`recent_passed_speed_candidate` is context only and not an active speed-reference mode in POC V1.** After passing a `speed_limit`-like event, POC V1 may retain the just-passed event's speed as a short-lived context value (`recent_passed_speed_candidate`). This memory is explicitly **context only** — it must not drive current-speed compliance UI, must not become an active provisional limit, must not be displayed as the current legal speed, and must not influence red / green compliance of the current speed. It exists to preserve the concept for future product logic and debugging.

9. **`pass_feedback_hold` or equivalent post-pass state is a temporary display / feedback state, not a new source of speed truth.** The temporary post-pass visual state that confirms how the previous event was passed (severity tiers, hold timing, camera-risk variant) is a feedback affordance, not a speed-reference mode. It does not redefine the target speed, does not supply a new target speed, and does not introduce a new authoritative source of speed truth. Its details (exact name, tier definitions, hold duration, camera-risk semantics) live in the planned `feedback-and-enforcement` area, not here.

10. **Enforcement tolerance is separate from speed reference.** The configurable enforcement-tolerance severity buffer that produces `enforcement_threshold_speed = target_speed_kmh + resolved_enforcement_tolerance_kmh` is a feedback / severity concept, not a speed-reference concept. It is used only for `unsafe_likely`, pass-feedback severity tiers, and camera-risk feedback. It must not redefine the target speed exposed by the speed reference, and it must not be substituted for the target speed inside normal guidance bands. Jurisdiction profiles (including any working Russia +20 km/h emulator default), profile-specific values, and the legal interpretation of any tolerance live in the planned `feedback-and-enforcement` area and remain WIP, not Canon here.

11. **Display hysteresis is separate from speed reference.** The small UI smoothing band around `target_speed_kmh` (`display_hysteresis_kmh`) is UI smoothing for the current-speed indicator's visual state, not a redefinition of the target. It does not change the target speed exposed by the speed reference, does not change the enforcement threshold, and does not change the deceleration profile values. Its exact value, range, and clear-hysteresis counterpart are tuning / implementation details and remain WIP, not Canon here.

12. **Speed reference must not consume route-provider speed, ETA, traffic speed, segment speed, or posted-limit data as RoadAhead truth.** Provider-supplied non-geometry signals are excluded from RoadAhead truth at the boundary level ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 8) and at the route-geometry level ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5 and 6). They may not be re-introduced as speed-reference truth, regardless of how the provider exposes them or how convenient they appear.

13. **Speed reference must preserve candidate / non-verified semantics inherited from `event-data` and `product-boundary`.** Because the speed reference's target value is sourced from a prepared candidate event ([`../event-data/event-data.md`](../event-data/event-data.md) truths 1, 4, 5, 10), it carries the same candidate / non-verified status. Routing a value through the speed reference does not upgrade it from candidate observation to verified, legally correct, or safety-certified truth. UI copy, debug output, and exports that surface the speed reference must remain consistent with the candidate / non-truth labeling established by [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) (truths 3, 4, 5, 6) and [`../event-data/event-data.md`](../event-data/event-data.md) (truths 1, 5, 10, 12).

14. **Exact timing, hysteresis, pass-hold duration, smoothing, and threshold values are tuning / implementation details, not Canon in this area.** Exact `pass_feedback_hold_s`, exact `display_hysteresis_kmh`, exact `clear_hysteresis_kmh`, exact `alpha_smoothing_ms`, exact `recent_passed_speed_candidate_ttl_s`, exact deceleration-profile values, exact reaction-time defaults, exact per-event-type lookahead guardrails, and exact jurisdiction-specific enforcement-tolerance values are explicitly out of scope for this Canon area. They live in WIP / research, future implementation issues, future ADRs, or — once validated — future Canon work in the planned `feedback-and-enforcement`, `ui-model`, and `tuning-and-validation` areas.

## Scope

This area covers:

- **Speed-reference state semantics at the principle level** — the rule that speed reference is RoadAhead's current driver-facing answer to "what target speed, if any, is the system orienting the driver around?".
- **Active POC V1 modes at the principle level** — `unknown` (no applicable target) and `approach_target` (an applicable speed-related event supplies a target). No other speed-reference state is active POC V1 Canon.
- **Candidate target speed semantics** — the rule that any target speed exposed by `approach_target` is event-derived candidate guidance context, not legal speed-limit truth.
- **Dependency on event applicability** — the rule that speed reference is evaluated only after event applicability has selected an eligible candidate; non-applicable candidates do not drive `approach_target`.
- **Provider-speed exclusion** — the rule that route-provider speed / ETA / traffic / segment speed / posted-limit data is excluded from RoadAhead speed truth, including at the speed-reference level.
- **Separation from enforcement tolerance** — the rule that enforcement tolerance is a feedback / severity concept, not a speed-reference concept, and may not be substituted for the target speed in normal guidance.
- **Separation from display hysteresis** — the rule that display hysteresis is UI smoothing only and does not redefine the target speed.
- **Separation from pass-feedback severity** — the rule that the temporary post-pass display / feedback state is not a new source of speed truth.
- **Deferral of `provisional_limit`** — the rule that `provisional_limit` is preserved as a future product concept but is not an active POC V1 speed-reference state.
- **Context-only nature of `recent_passed_speed_candidate`** — the rule that any post-pass memory of a just-passed speed is context only, not an active speed-reference mode and not displayed as the current legal speed.
- **Temporary display-state nature of pass feedback / hold state** — the rule that the post-pass hold state is a feedback affordance, not a speed-reference mode.
- **Candidate / non-verified truth boundary** — the rule that speed-reference values inherit candidate / non-verified semantics from `event-data` and `product-boundary` and do not become verified or legally correct by being routed through the speed reference.

## Product rules

These rules are normative. They follow from the Canon truths and constrain implementation, data behavior, and UX:

- **Do not show or use route-provider speed / ETA / traffic / segment / posted-limit data as RoadAhead speed reference.** Provider-supplied non-geometry signals are excluded from RoadAhead truth ([`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 8; [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truths 5 and 6); routing them through speed reference is a boundary violation. (From truths 2, 12.)

- **Do not treat event-derived target speed as legal truth.** The `approach_target` target speed is candidate guidance context sourced from a prepared candidate event ([`../event-data/event-data.md`](../event-data/event-data.md) truths 1, 5). Product copy, UI labels, debug strings, and exports must not present it as the current legally valid speed limit. (From truths 1, 5, 13.)

- **Do not compute speed reference before event applicability.** The speed reference is evaluated only on candidates that have already passed the route / path / direction applicability gate ([`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1, 11). A non-applicable candidate must not drive `approach_target` or supply a target speed. (From truths 4, 6.)

- **If no applicable speed-related event exists, the speed reference is `unknown`.** Absence of an applicable speed-related event is the correct condition for the `unknown` state. The system must not invent a target speed in the absence of an applicable event, and must not display a target speed as a placeholder. (From truths 3, 4, 6, 7, 8.)

- **`approach_target` may be active only for an applicable event with a target speed.** A candidate event that has no event-derived target speed (for example, an event type that does not carry one) does not drive `approach_target`. The combination of "applicable" and "carries a target speed" is required for `approach_target` to be active. (From truths 4, 5, 6.)

- **Do not use enforcement tolerance to redefine target speed.** The enforcement-tolerance severity buffer must not be substituted for `target_speed_kmh` inside the speed reference, inside normal guidance bands, or anywhere else that needs "the speed RoadAhead is orienting the driver around". `enforcement_threshold_speed` is a feedback / severity-only derivation, not a speed-reference value. (From truth 10.)

- **Do not use display hysteresis to redefine target speed.** Display hysteresis is UI smoothing only. It does not change the target speed exposed by the speed reference, does not change the enforcement threshold, and does not change the deceleration profile values. (From truth 11.)

- **Do not treat pass-feedback hold as a new speed source.** The temporary post-pass visual state — including any camera-risk variant — is a feedback affordance only. It does not redefine the target speed, does not introduce a new authoritative speed, and does not become a new speed-reference mode. (From truth 9.)

- **Keep Russia +20 km/h and any other jurisdiction profile out of speed-reference truth.** Jurisdiction-specific tolerance values (including any working Russia +20 km/h emulator default) live in the planned `feedback-and-enforcement` area as configurable severity profiles. They are working defaults, not legal claims, and must not be promoted into speed-reference truth. (From truths 1, 10, 14; consistent with [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) truth 4.)

- **Keep exact thresholds, timing, and tuning out of this Canon area.** No exact `pass_feedback_hold_s`, no exact `display_hysteresis_kmh`, no exact `clear_hysteresis_kmh`, no exact `alpha_smoothing_ms`, no exact `recent_passed_speed_candidate_ttl_s`, no exact deceleration-profile value, no exact reaction-time default, and no exact enforcement-tolerance value is Canonized by this area. Promotion of any such value requires emulator-based scenario evidence and a deliberate Canon / ADR PR per [`../../README.md`](../../README.md) "Promotion rule". (From truth 14; consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10.)

## Implementation-facing implications

These implications are intentionally high-level and stable. Concrete code, schema, debug, and UX shape belongs to future implementation slices or WIP / research:

- **Speed-reference implementation should consume eligible applicable events, not raw events or raw provider / source data.** The input to the speed reference is the event-applicability gate's accepted candidate(s). Raw vendor source rows ([`../event-data/event-data.md`](../event-data/event-data.md) truths 2, 4), provider-native route objects ([`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md) truth 7), and non-applicable candidates ([`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 1, 11) must not flow into the speed reference.

- **Speed-reference output should be usable by UI / feedback / enforcement layers, but those layers must not mutate the underlying target speed.** Downstream layers (current-speed indicator, urgency ring, pass-feedback / camera-risk feedback, enforcement-profile evaluation) read the speed reference; they do not redefine its target. The same `approach_target` target speed must be visible identically across normal guidance, debug, and feedback evaluation.

- **Feedback / enforcement may compare current speed to speed reference plus profile tolerance, but tolerance does not change speed reference.** `enforcement_threshold_speed = target_speed_kmh + resolved_enforcement_tolerance_kmh` is a feedback / severity-only derivation owned by the planned `feedback-and-enforcement` area. The speed reference exposes the target; the feedback / enforcement layer composes the threshold from it. They are not the same field and must be displayed separately in any debug surface.

- **Hysteresis may stabilize display state, but does not change target speed semantics.** A UI smoothing band around the target prevents flicker in the visible current-speed indicator. It does not change the target the speed reference is exposing and does not change the urgency-band computation against that target.

- **Debug output may show speed-reference state and source candidate, but debug display does not imply legal correctness.** A validation-emulator debug surface that exposes the active speed-reference state, the source candidate event, and the candidate-derived target speed remains a candidate / non-verified surface ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 7, 8, 9). The presence of a target speed in debug is not a legal claim and does not promote any value to verified truth.

- **Implementation slices needing thresholds, timing, smoothing, or hysteresis should cite WIP / research or future tuning-and-validation Canon — not this area.** This Canon area commits to speed-reference principles, not to numbers, formulas, or tier definitions. Slices that need such detail cite [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md), [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md), [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), the planned `feedback-and-enforcement` / `tuning-and-validation` areas (once they exist), or a future ADR.
