# Tuning and Validation

## Purpose

This area defines RoadAhead's stable **methodology** for tuning, validation, and promotion of numeric values, thresholds, timings, deceleration profiles, hysteresis bands, smoothing constants, lookahead guardrails, jurisdiction profile values, and visual / animation parameters. It is the area that answers — at the methodology level — the single question: **how does a numeric value move from a working assumption, an emulator default, or a research starting point to Product Canon?**

This area **does not promote any numeric value to Canon**. At the current stage of the RoadAhead POC V1 project, **RoadAhead has no numeric tuning value that is Product Canon**. Every threshold, timing, hysteresis band, smoothing constant, lookahead guardrail, deceleration value, reaction-time value, enforcement-tolerance value, jurisdiction profile value, scenario sweep matrix entry, and acceptance gate currently visible in the WIP product spec, the companion decision workbook, or any of the five Issue #20 research recommendations is — at this point — a **working assumption**, an **emulator default**, or a **tuning candidate**. They are useful as starting points for emulator validation, debug visibility, and review; they are **not** stable product truth.

Numeric values require **validation evidence** before Canon promotion. The first validation surface for that evidence is the **POC V1 interactive web route emulator** ([`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 1, 4, 10). Emulator evidence may inform later promotion, but emulator evidence is not itself Canon and does not automatically promote any value (consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10 and the promotion rule in [`../../README.md`](../../README.md)). Later **practical / real-world tests** — on mobile, on real devices, with real drivers, in real road conditions — may be required before certain values can be promoted with confidence; the exact shape of that practical-test phase is itself WIP and not Canonized here.

This area sits alongside every other existing Canon area: it does not redefine any of their truths. It governs only the **method** by which numeric values from any of those areas might in the future be promoted. The exact scenario matrices, metrics, pass / fail criteria, statistical models, recording schemas, and acceptance gates that a future emulator-driven validation pipeline would use are themselves **WIP until defined and validated** — this area Canonizes the principle that such a methodology must exist before numbers are Canonized, not the exact mechanics of that methodology.

## Canon truths

The truths below are stable RoadAhead **methodology-level** commitments about tuning and validation. They are deliberately short, methodology-only, and exact-value-free. No numeric value is promoted by any truth below.

1. **No numeric tuning value is Product Canon until it has been explicitly validated and promoted through a deliberate Canon / ADR PR.** The default status of every numeric threshold, timing, hysteresis band, smoothing constant, lookahead guardrail, deceleration value, reaction-time value, enforcement-tolerance value, jurisdiction profile value, and visual / animation value is WIP / research / emulator default, **not Canon**.

2. **WIP and research numeric values are working assumptions, emulator defaults, or tuning candidates — not stable product truth.** Numbers that appear in the WIP product spec, in the companion decision workbook, in any of the five Issue #20 research recommendations, or in any future research input are inputs to a later Canon review. They are not Canon by virtue of being written down.

3. **Emulator validation is required before any numeric value can be promoted to Canon.** Tuning candidates must be exercised in the POC V1 interactive web route emulator (the first validation surface, per [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truths 1 and 4) under the relevant scenarios before they can be considered for Canon promotion. A number that has not been exercised in the emulator is not promotable.

4. **Scenario sweeps are the primary POC V1 mechanism for evaluating tuning candidates.** A scenario sweep is a structured, reproducible matrix of emulator runs across speeds, targets, distances, event types, profiles, and route geometries, with debug-visible per-run records. POC V1 evaluates tuning candidates through scenario sweeps rather than by picking a value in isolation.

5. **Validation evidence must record, at minimum, the scenario, the active tuning / profile configuration, the observed behavior, and a reviewer conclusion.** Evidence that does not name its scenario, does not name its configuration, does not record the observed behavior, or does not record a deliberate human reviewer conclusion is not promotion-grade evidence. The exact schema for these records remains WIP.

6. **A numeric value may be useful in the emulator without being Canon.** Emulator defaults, debug-visible tuning fields, scenario sweep starting points, and exploration ranges are useful for validation work even when they are not Canon. Usefulness in the emulator is **not** a promotion path on its own.

7. **Emulator evidence may inform Canon promotion but does not automatically promote values.** Running a scenario in the emulator, observing acceptable behavior, and recording the result are inputs to a later Canon / ADR review. They do not by themselves Canonize the values exercised; promotion still requires an explicit, reviewed Canon / ADR PR (consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 10 and the promotion rule in [`../../README.md`](../../README.md)).

8. **Promotion of any numeric value requires a deliberate Canon / ADR PR.** A Canon / ADR PR that promotes a numeric value must cite the validation evidence on which it relies, must explain what was tested and what conclusion was reached, and must update the relevant Canon area's `Still WIP / not Canon` and `Source traceability` sections. Promotion does not happen as a side effect of any other change.

9. **Human-factors, safety, legal, and jurisdictional claims require explicit source / review beyond emulator observation.** Emulator observation cannot, by itself, support a claim about real-world driver reaction time, real-world safe braking, real-world safe display distance, human-factors certification, real-world safety, the legal validity of any speed limit, the legal validity of any enforcement tolerance in any jurisdiction, or any equivalent real-world claim. Such claims require sources and review that are explicitly beyond the scope of emulator validation and remain WIP / future work.

10. **Tuning values must preserve the existing product boundaries: non-navigator, non-anti-radar, non-legal authority, non-safety-certified.** A tuning value that, by its size, shape, or visual effect, would push the driver-facing surface toward navigator behavior, anti-radar / enforcement-evasion semantics, legal-authority framing, or safety-certification framing is **not** promotable, regardless of how well it behaves in the emulator. The boundary commitments in [`../product-boundary/product-boundary.md`](../product-boundary/product-boundary.md) (truths 2, 3, 4, 5) are upstream of tuning.

11. **Tuning values must not silently redefine upstream Canon concepts** such as the target speed exposed by the speed reference, the route / path / direction applicability gate, the candidate / non-verified nature of external event data, the geometry-only nature of route-provider input, the separation between target speed and enforcement tolerance, the separation between display hysteresis and enforcement tolerance, the separation between pass-feedback severity and the speed reference, or the conservative posture under ambiguity. A tuning change that would re-author any of those concepts is not a tuning change; it is a Canon change and requires the corresponding Canon / ADR PR.

12. **Tuning, configuration, and session values are not base event truth.** Tuning config, enforcement-profile state, threshold-tuning state, scenario-sweep state, and validation-run state are per-session runtime values; they must not be persisted onto the base prepared candidate event record (consistent with [`../event-data/event-data.md`](../event-data/event-data.md) truth 11 and the route-specific derived-data boundary across [`../route-geometry/route-geometry.md`](../route-geometry/route-geometry.md), [`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md), and [`../feedback-and-enforcement/feedback-and-enforcement.md`](../feedback-and-enforcement/feedback-and-enforcement.md)).

13. **Validation should cover normal, edge, and ambiguity scenarios before values are promoted.** A tuning value is not promotable on the basis of well-behaved normal scenarios alone. The scenario set considered for promotion must also exercise edge cases (very low / very high speeds, very short / very long distances, very small / very large speed deltas, chained events arriving close in time) and ambiguity scenarios (parallel carriageways, ramps, branches, T-junctions, bidirectional / unknown source direction semantics) consistent with [`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) truths 9, 10, 11. The exact scenario matrix remains WIP.

14. **Failed, inconclusive, or conflicting scenario results must keep the value WIP.** Scenario evidence that fails, that is inconclusive, that conflicts with other scenarios, or that produces behaviors the reviewer cannot confidently explain is not a basis for Canon promotion. The correct status for the value is "remains WIP, with the failure / inconclusive / conflict recorded as input to the next iteration".

15. **Numeric values may be revised or deprecated when new evidence appears.** A value that becomes Canon at one point may be revised, demoted to WIP, or deprecated by a later deliberate Canon / ADR PR when new emulator evidence, practical-test evidence, or upstream Canon change makes the previous value no longer correct. Revising or deprecating a Canon numeric value is a Canon change, not a tuning change.

16. **The exact scenario matrices, metrics, formulas, statistical models, recording schemas, and acceptance gates of the methodology are themselves WIP until defined and validated.** This area Canonizes the principle that a methodology must exist before numeric values are Canonized; it does **not** Canonize the precise shape of that methodology. The exact axes of the scenario sweep, the exact per-run record fields, the exact pass / fail metric, the exact acceptance gate, the exact statistical interpretation rules, and the exact practical-test protocol remain WIP / research / future implementation work.

> **Important — what is deliberately NOT Canonized by these truths.** None of the truths above promote any numeric value. In particular, **no** specific reaction time, **no** specific deceleration value (smooth / normal / strong / emergency), **no** specific lookahead distance (minimum display, maximum lookahead, per-event-type guardrail), **no** specific display or clear hysteresis value, **no** specific enforcement tolerance value (including the Russia +20 km/h working POC default), **no** specific pass-feedback hold duration, **no** specific camera-risk pulse / blink cadence, **no** specific alpha smoothing value, **no** specific UI animation / ring alpha / visual intensity value, **no** specific scenario matrix entry, and **no** specific pass / fail metric is Canonized by this area. **No** safety, legal, or human-factors claim is Canonized by this area.

## Scope

This area covers:

- **Methodology for validating tuning candidates** — the principle that numeric values are validated through a structured, reproducible, debug-visible process, not by assertion.
- **Status of WIP / research numeric values as candidates only** — the rule that values appearing in the WIP product spec, the companion decision workbook, the five Issue #20 research recommendations, and any future research input are working assumptions, emulator defaults, or tuning candidates, not Canon.
- **Evidence requirements for promotion** — the rule that promotion-grade evidence must record scenario, configuration, observed behavior, and reviewer conclusion.
- **Scenario sweep as the primary POC V1 evaluation mechanism** — the rule that POC V1 evaluates tuning candidates through scenario sweeps, not through isolated value choices.
- **Emulator-first validation** — the rule that the POC V1 interactive web route emulator is the first validation surface; later practical / real-world tests may be required before final confidence on certain values.
- **Deliberate promotion rule** — the rule that promotion of any numeric value requires an explicit Canon / ADR PR citing validation evidence, not a side effect of any other change.
- **Separation between tuning / config / session state and base event truth** — the rule that tuning values, profile values, hysteresis values, smoothing values, scenario-sweep state, and validation-run state are per-session runtime and must not be persisted onto the base candidate event record.
- **Preservation of upstream Canon boundaries** — the rule that no tuning change may push RoadAhead toward navigator, anti-radar, legal-authority, or safety-certification framing, and that no tuning change may silently redefine an upstream Canon concept (target speed, applicability, candidate-data status, geometry-only provider boundary, conservative posture under ambiguity).
- **Handling of failed / inconclusive / conflicting evidence** — the rule that such evidence keeps the value WIP, with the failure / inconclusive / conflict recorded as input to the next iteration.
- **Future revision / deprecation** — the rule that numeric values may be revised or deprecated by a later deliberate Canon / ADR PR when new evidence appears.

## Product rules

These rules are normative. They follow from the Canon truths and constrain how Canon, ADR, WIP, research, and implementation work treat numeric values.

- **Do not copy a WIP / research numeric value into Canon merely because it appears in a recommendation doc.** A number that is present in [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md), in [`../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md`](../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md), in [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), in [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md), in [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md), in [`../../../research/roadahead-route-geometry-provider-recommendation.md`](../../../research/roadahead-route-geometry-provider-recommendation.md), or in [`../../../research/roadahead-prepared-event-store-recommendation.md`](../../../research/roadahead-prepared-event-store-recommendation.md) is **not** Canon by virtue of being written down. Promotion requires validation evidence and an explicit Canon / ADR PR. (From truths 1, 2, 7, 8.)

- **Do not present emulator defaults as validated product truth.** Emulator default values (including any value visible in a debug / config surface, any value used as a scenario-sweep starting point, and any value seeded into the first emulator slice) must be labeled as defaults / candidates in code, configuration, documentation, copy, debug, exports, and reviewer-facing surfaces — not as validated product truth. (From truths 2, 6, 7.)

- **Do not use unvalidated values to make legal, safety, or human-factors claims.** A tuning value cannot, by itself, support a claim about the legal validity of a speed limit, the legal validity of an enforcement tolerance in any jurisdiction, the legal validity of any camera-related behavior, safety certification, comfortable / safe braking behavior, safe display distance, real-world driver reaction time, or any equivalent real-world claim. Such claims require sources and review beyond emulator observation and remain WIP / future work. (From truths 9, 10.)

- **Any PR that promotes a numeric value to Canon must cite the validation evidence on which it relies and explain what was tested.** A promotion PR must state the scenarios that were exercised, the active tuning / profile configuration in use, the observed behavior, the reviewer conclusion, and where the recorded evidence lives. A promotion PR that does not cite evidence or does not explain what was tested is not promotable. (From truths 5, 7, 8.)

- **Scenario evidence should identify the route, the event set, the speed profile, the tuning configuration, the observed behavior, and the reviewer conclusion.** This is the minimum information a reviewer needs to be able to assess whether the recorded behavior supports the promotion of any specific value. The exact schema of this record is itself WIP. (From truths 4, 5, 13.)

- **If evidence is missing, inconclusive, or conflicting, keep the value WIP.** A value remains WIP — not promoted — when scenario evidence has not been run, when scenario evidence is inconclusive, when scenarios produce conflicting outcomes, or when the reviewer cannot confidently explain the observed behavior. The correct response is to record the missing / inconclusive / conflicting state and iterate, not to promote on partial evidence. (From truths 13, 14.)

- **Keep runtime tuning configuration separate from base event data.** The active tuning configuration, the active enforcement profile, the active threshold-tuning values, scenario-sweep state, and validation-run state are session / runtime data; they must not be persisted onto the base prepared candidate event record. The active configuration may be recorded in a per-session run artifact for reproducibility, but that record belongs to the run artifact, not to the base event. (From truth 12; consistent with [`../event-data/event-data.md`](../event-data/event-data.md) truth 11 and [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md) §11.)

- **Keep target speed, enforcement tolerance, display hysteresis, feedback severity / tier, and UI visual timing as distinct concepts during validation.** Validation evidence must not collapse these concepts into a single field, a single comparison, or a single visible value. Each concept must be separately recorded in the debug / config surface so a reviewer can verify that changing one does not silently move another. (From truth 11; consistent with [`../speed-reference/speed-reference.md`](../speed-reference/speed-reference.md) truths 10, 11, [`../feedback-and-enforcement/feedback-and-enforcement.md`](../feedback-and-enforcement/feedback-and-enforcement.md) truths 2, 3, 5, 10, and [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md) §3, §7.)

- **Document rejected or revised values when they materially affect future decisions.** When scenario evidence rejects a candidate value, when a previously useful starting default is revised, or when a previously Canon value is demoted / deprecated, the decision should be recorded — in the relevant Canon area's `Still WIP / not Canon` section, in the relevant WIP / research doc, or in an ADR — so that future review can understand the history and avoid re-litigating the same question without new evidence. (From truths 14, 15.)

## Implementation-facing implications

These implications are intentionally high-level and stable. Concrete code, scenario-sweep harness, debug surface, recording schema, and acceptance-gate implementation belong to future implementation slices or WIP / research:

- **The POC V1 interactive web route emulator should support scenario sweeps and record enough debug / state information to support later validation decisions.** Concretely, the emulator should expose the active tuning configuration, the active enforcement profile, the active applicability configuration, the raw and smoothed simulated speed, the active applicable primary / secondary event(s), the route-projection / tangent / direction-delta state, the urgency-band selection, the feedback severity / tier state, and the camera-risk variant state — all separately inspectable. The exact debug field list, the exact run protocol, and the exact recording schema remain WIP (consistent with [`../validation-emulator/validation-emulator.md`](../validation-emulator/validation-emulator.md) truth 7 and Still WIP / not Canon).

- **Implementation may start with WIP defaults, but code, comments, configuration, and documentation must label them as defaults / candidates, not Canon values.** A POC V1 emulator slice that hard-codes a working default for `pass_feedback_hold_s`, for `display_hysteresis_kmh`, for `decel_emergency_mps2`, for a per-event-type lookahead guardrail, or for any other numeric value must label that value in code, in comments, in any config surface, in any debug surface, and in any reviewer-facing surface as a working default / tuning candidate. A naming convention such as "default", "starting", "candidate", or "wip" — applied consistently across emulator surfaces — is appropriate; the exact naming convention is implementation detail.

- **Debug and QA surfaces should expose enough state to explain why a value behaves acceptably or poorly.** A reviewer should be able to inspect, for any given scenario run, the inputs that drove the behavior (raw current speed, distance to event, target speed, applicable event), the intermediate values the model computed (required deceleration, projected distance, direction delta, branch state), the resulting visible state (urgency band, feedback tier, camera-risk variant, hysteresis state), and the active configuration (tuning config, enforcement profile, applicability configuration). The exact debug field list and surface layout remain WIP.

- **Future implementation issues should avoid treating WIP values as final acceptance criteria.** Implementation tickets that depend on a numeric value should depend on the **behavior** the value produces, not on the value itself. Acceptance criteria such as "the urgency ring lights up at the expected severity given the active deceleration profile" are appropriate; acceptance criteria such as "`pass_feedback_hold_s = 2.0` exactly" are not, until the value has been promoted to Canon.

- **Numeric promotion happens in later Canon / ADR PRs after evidence is available.** Each future Canon / ADR PR that promotes a numeric value to Canon should: cite the scenario evidence on which it relies; explain what was tested and what conclusion was reached; identify the upstream Canon area whose `Still WIP / not Canon` section is being moved; update that area's `Still WIP / not Canon` and `Source traceability` sections; and remain consistent with this area's methodology. Promotion is a deliberate act; it is not a side effect of any other change.

- **Implementation slices that need exact tuning, profile, hysteresis, smoothing, projection, applicability, or visual values should cite the relevant research and WIP docs, not this Canon area.** This area commits to tuning-and-validation **methodology**, not to numbers, formulas, tier boundaries, jurisdiction values, or visual details. Slices that need such detail cite [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md), [`../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md`](../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md), [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md), [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md), [`../../../research/roadahead-route-geometry-provider-recommendation.md`](../../../research/roadahead-route-geometry-provider-recommendation.md), [`../../../research/roadahead-prepared-event-store-recommendation.md`](../../../research/roadahead-prepared-event-store-recommendation.md), or a future ADR — and they must continue to treat any cited value as a working default / candidate, not as Canon.

## Still WIP / not Canon

The items below are deliberately **not promoted to Canon** by this PR. They are listed by **name** of the value, not by exact numeric value, so that this Canon area does not silently anchor any specific number. Every item below remains a working assumption, an emulator default, a tuning candidate, or a future research / implementation question until validated evidence exists and a deliberate Canon / ADR PR promotes it.

- **All numeric values currently present in WIP / research.** Every numeric value in [`../../wip/roadahead-poc-v1-three-circle-assistant.md`](../../wip/roadahead-poc-v1-three-circle-assistant.md), [`../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md`](../../wip/roadahead-poc-v1-initial-product-decisions-workbook.md), [`../../../research/roadahead-threshold-tuning-recommendation.md`](../../../research/roadahead-threshold-tuning-recommendation.md), [`../../../research/roadahead-enforcement-profile-recommendation.md`](../../../research/roadahead-enforcement-profile-recommendation.md), [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md), [`../../../research/roadahead-route-geometry-provider-recommendation.md`](../../../research/roadahead-route-geometry-provider-recommendation.md), and [`../../../research/roadahead-prepared-event-store-recommendation.md`](../../../research/roadahead-prepared-event-store-recommendation.md) — without exception — is a candidate, not Canon.

- **`reaction_time_default_s`** — the modeled default reaction time used to compute reaction distance in the required-deceleration formula. Working assumption, not human-factors certification, not safety guidance.

- **`reaction_time_high_speed_s`** — the secondary modeled reaction-time configuration used in high-speed / poor-visibility debug scenarios. Working assumption, not human-factors certification.

- **`decel_smooth_mps2` / `decel_normal_mps2` / `decel_strong_mps2` / `decel_emergency_mps2`** — the named deceleration profile values used to map required deceleration to urgency bands. Emulator tuning categories, not vehicle braking specifications, not comfort studies.

- **Lookahead / minimum / maximum display distances** — the per-event-type minimum display distance and maximum lookahead distance for `speed_limit`, `static_camera`, `road_bump`, and any future event type. Distance-based POC V1 starting form; a time-based form is a future possibility, not a decision.

- **Direction delta thresholds** — the direction-delta accept / warn / ambiguous / reject thresholds used by the direction-applicability evaluation. WIP per [`../event-applicability/event-applicability.md`](../event-applicability/event-applicability.md) Still WIP / not Canon and [`../../../research/roadahead-direction-applicability-recommendation.md`](../../../research/roadahead-direction-applicability-recommendation.md) §4.

- **Projection accept / warn / reject thresholds** — the route-projection accept / warn / reject distances and the pass-or-behind tolerance used by the route-projection step.

- **Branch ambiguity thresholds** — the branch-zone radius, projection-competitor delta, competitor-heading delta, and related parameters used by branch / ramp / parallel-carriageway / intersection ambiguity handling.

- **`display_hysteresis_kmh` / `clear_hysteresis_kmh`** — the small UI smoothing band around target speed and the corresponding clear-hysteresis band. UI smoothing only; explicitly not enforcement tolerance.

- **`enforcement_tolerance_kmh` and the Russia +20 km/h profile** — the configurable severity buffer used by feedback / severity computations, and the working Russia-focused POC default. Working emulator profile only; **not** a legal claim.

- **`pass_feedback_hold_s`** — the duration for which post-pass feedback (Tier 1 / Tier 2 / camera-risk variant) remains visible. Working default; the interruption policy when a more urgent upcoming event arrives during the hold also remains WIP.

- **Pass-speed sampling approach** — the rule used to sample `pass_speed_kmh` at the pass point (raw authoritative simulated speed by default, with any debug variant clearly labeled).

- **`unsafe_likely` formula thresholds** — the precise numeric formula and comparator deceleration value above which `unsafe_likely` fires, along with the interaction with the pre-pass unrecoverable-distance trigger. Severity signal only; not a legal verdict, not a safety certification.

- **`alpha_smoothing_ms`** — the time constant used to smooth the displayed current-speed indicator. Affects displayed value only; the raw value drives the model.

- **Ring alpha and visual intensity parameters** — the urgency-ring thickness, alpha ramp values, intensity values per band, and equivalent driver-facing visual intensity parameters.

- **Camera-risk pulse / blink timing** — the camera-icon pulse cadence, pulse count, blink rules, and any color treatment for the camera-risk visual variant. Bounded to "possible camera risk" semantics; visual cadence remains WIP.

- **Exact scenario sweep matrix** — the exact set of speeds, targets, distances, event types, enforcement profiles, route geometries, and event-chain sequences that a future scenario sweep would run.

- **Exact acceptance gates** — the exact pass / fail metric, the exact statistical interpretation, the exact reviewer-conclusion shape, and the exact diffing / re-run rules used to gate Canon promotion of any value.

- **Exact legal / safety / human-factors validation protocol** — the exact sources, reviewers, jurisdictions, evidence requirements, and decision process under which any future legal, safety, or human-factors claim might be made. No such protocol is Canonized here; any future claim of this kind requires a deliberate, separately-reviewed PR.

All items above remain WIP until validated evidence exists and a deliberate Canon / ADR PR — consistent with the methodology truths in this area and with the promotion rule in [`../../README.md`](../../README.md) — promotes them.
